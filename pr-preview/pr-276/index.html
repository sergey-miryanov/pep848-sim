PEP 848: the incremental cycle collector

PEP 848 proposes a generational incremental cycle collector for CPython. This page runs a small Python simulator of it, and of the legacy collector beside it, in your browser: the widget below runs the workload you pick under both collectors and draws what each does. In the playground you can change any part of a workload, write a shape of your own in Python and send a run by its link. The guide explains the PEP a chapter at a time, and the presets page sets each preset's collections beside its benchmark's.

The first runs wait a few seconds while Pyodide, the Python that runs in the browser, downloads and starts.

Reading the widget

Both runs allocate the same objects in the same order: the legacy collector on the left, the incremental collector on the right. Each simulated object stands for 1 kB of real objects, and the allocation clock along the bottom counts the MB a run has allocated.

Rest the pointer on a panel to read its values in both columns: the heap before and after the nearest collection, the work budget that collection left, or the work in the bar under the pointer. Escape hides them until you move on. From the keyboard, tab to a panel and step from one collection or bar to the next with the arrow keys, or to the first and the last with Home and End. A screen reader reads out each one's values.

Workload
Pick the workload both runs share. Each keeps the values you gave its controls while the page stays open, and the page's address names the one shown, so a link opens it. The widget holds the runs of the last 16 workloads and values you tried, and draws them at once when you come back to one.
Controls
Move a slider to pick a value, and release it to run both collectors again with it. The workload's sliders come first, then the collector settings: the three thresholds of gc.set_threshold(), which every workload shares. Under threshold0 and threshold1 you read the young generation they make in the incremental collector, and only the legacy collector reads threshold2. Under them, Collector constants opens the numbers no Python API changes: the incremental collector's initial work budget and freed-credit multiplier, and the legacy collector's long-lived ratio.
Object graph
A few objects of each structure the workload builds, linked as its shape links them, under sys or the frame that holds it. A number marks each structure's first object, and the list under the controls gives its size and when the workload builds and drops it. A red link lies on a cycle, so dropping its structure leaves cyclic garbage for a collection to find.
Figures
Each run's peak work, the most work one collection the runtime started did, which stands in for the worst pause; its peak uncollected garbage; its work per MB, which stands in for the collector's overhead; its yield, the share of the objects it examined that were cyclic garbage; its collections; and its gen 2 collections or sweeps.
Heap by space
The heap in MB, in lanes on the allocation clock. The top lane draws the whole heap and its reachable part, and shades the gap between them, the uncollected garbage. The lanes below draw the nursery, the aging generation and the old generation. In the incremental collector's column, the old generation's lane stacks its pending and visited spaces. A tick at the foot of the top lane marks each gc.collect() call, and a dashed rule across the panels marks shutdown.
Work
The objects each run's collections marked, saw survive and freed, summed over stretches of a few MB. The work of full collections, which gc.collect() and shutdown run, stacks faded above the runtime's own.
Work budget
The scanning the incremental collector owes, work_to_do in the PEP. Young collections add to it and old collections spend it; at zero or below, old collections do no work until young ones raise it again.

The workloads

Each workload is a preset, modelled on a worker of a pyperformance benchmark and checked against that benchmark's yield. The guide's sections run them.

The widget opens on xml_etree_parse, which models a worker of the xml_etree benchmark's parse task. Four times over, it builds a tree of 5,103 elements, then parses it 60 times, from a file and from bytes in turn, and each parsed tree replaces the last of its kind. C code parses each one, so a collection that falls due during a parse waits until it ends. No element links back to its parent, so refcounting frees each tree as the next replaces it, and a collection that examines a tree finds it alive. Before shutdown, the collections find no cyclic garbage beyond a few cycles that start-up lets go of. Its workload's slider sets the parsed trees' size.

create_gc_cycles models a worker of the benchmark of that name. After start-up, each of its 512 loops calls gc.collect(), builds 100 rings of 21 objects, drops them and calls gc.collect() again, and shutdown ends the run. The calls reset the countdown to the next collection so often that the runtime starts none of its own once the loops begin.

json_loads models a worker of the benchmark of that name, which calls json.loads 60 times a loop on three JSON strings. No result holds a cycle, and each goes as its call returns, so the runtime's collections find no cyclic garbage beyond a few cycles that start-up lets go of. Nothing calls gc.collect() before shutdown. Over so few collections, each one the incremental collector runs before shutdown is idle: its young collections take aging spaces still empty this early, and its old collections have no work budget to spend. Lower threshold0 to give it more collections.

async_tree_io_tg models a worker of the benchmark of that name. Four times over, it starts a tree of 55,987 asyncio tasks, six levels of six under the root, each level under a TaskGroup, and each leaf sleeps 50 ms. No task links back to the one that started it, so refcounting frees the tree as the run ends, and before shutdown the collections find no cyclic garbage beyond a few cycles that start-up lets go of. sys reaches the tree through the event loop, so the incremental collector's old collections mark it a budget at a time, and its peak work stays far below the legacy collector's, whose gen 1 collections take the nursery and the aging generation whole. As each run ends and its tasks finish, the legacy collector's gen 0 collections examine more than while the tree grows. The churn's lifetimes remain placeholders.

connected_components models a worker of the networkx benchmark of that name. As its module loads, it imports networkx and reads the Amazon co-purchasing graph, 262,111 products and 899,792 edges, into 1.4 million dicts that stay in the module's globals. Each of its four loops then walks the graph to count its components, and each iterator the walk makes goes once a node's neighbours run out. read_adjlist's frame holds the graph while it loads, so sys reaches none of it, and the incremental collector's old collections examine it in increments, each about twice the last: its peak work passes the legacy collector's. Once the module holds the graph, no young collection finds a survivor to add to the work budget, and the old collections go idle with the whole graph back in pending. The legacy collector runs no gen 2 collection before shutdown. The graph's dicts hold no cycle, but the module's globals lie on one with its functions, so the graph turns into cyclic garbage once the module goes, and the second shutdown collection frees it. The churn that outlives a collection remains a placeholder.

More
